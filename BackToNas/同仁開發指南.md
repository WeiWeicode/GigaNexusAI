# GigaNexus 同仁開發指南:第一次設定與分支流程

> 從 NAS 拉取專案後**先讀這份**。照著做完「一、第一次設定」就能開始開發;日常開發依「二、分支與合併流程」進行。
> 各專案的程式規範寫在該專案的 `AGENT.md`;使用 AI 開發時,AI 也會依 `AGENT.md` 的規則工作。

---

## 一、第一次設定(每台電腦做一次)

### 1. 設定 Git 身分

GitLab 上每筆提交顯示的作者,取自您電腦的 Git 設定。專案本身**沒有**設定作者,不設定的話提交會失敗,或顯示成電腦名稱。

```bash
git config --global user.name "王小明"
git config --global user.email "xiaoming@gigasolar.com.tw"
```

確認:

```bash
git config --global --list
```

### 2. 建立自己的 SSH 金鑰並加到 GitLab

推送時 GitLab 依 SSH 金鑰判斷「是誰推的」。**每人用自己的金鑰,不要共用別人的金鑰**,否則 GitLab 上的紀錄會全部算在同一個人身上。

1. 產生金鑰(一路按 Enter 即可;已有 `~/.ssh/id_ed25519` 的人跳過這步):

   ```bash
   ssh-keygen -t ed25519 -C "xiaoming@gigasolar.com.tw"
   ```

2. 顯示公鑰並整段複製:

   ```bash
   cat ~/.ssh/id_ed25519.pub
   ```

3. 登入 GitLab(`http://10.10.130.123`)→ 右上角頭像 → **Preferences** → **SSH Keys** → **Add new key**,貼上後儲存。

4. 測試連線,看到 `Welcome to GitLab, @您的帳號!` 就成功:

   ```bash
   ssh -T -p 2222 git@10.10.130.123
   ```

### 3. 確認專案的 GitLab 位址

NAS 拉下來的專案已把 `origin` 設為公司 GitLab,確認一下即可:

```bash
cd D:\GigaNexusAI\giga-Portal
git remote -v
```

應該看到 `ssh://git@10.10.130.123:2222/giganexus/...`。若出現 `github.com`,請告知專案負責人。

> **程式碼以公司 GitLab 為準**:分支、MR、CI/CD 都在 GitLab。GitHub 只是專案負責人個人的備份,您不需要設定,也不要推送到 GitHub。

### 4. 設定 npm 套件 Token(要 `npm install` 的專案才需要)

`@giganexus/*` 套件放在公司 GitLab 的 npm Registry,安裝時需要 Token。請建立**自己的** Token,不要向別人借:

1. GitLab → 頭像 → **Preferences** → **Access tokens** → **Add new token**
2. 名稱填 `npm`,權限勾 **`read_api`**,設定到期日後建立,複製 Token(只會顯示一次)
3. 在 PowerShell 寫入使用者環境變數(把 `<Token>` 換成剛剛複製的值):

   ```powershell
   [Environment]::SetEnvironmentVariable("GITLAB_NPM_TOKEN", "<Token>", "User")
   ```

4. **關掉所有終端機與編輯器再重新開啟**,環境變數才會生效。

### 5. 之後怎麼更新程式碼

- **程式碼一律用 `git pull` 從 GitLab 更新**,不要再用 NAS 拉取。
- NAS 只用在兩種情況:第一次建置環境,以及負責人通知 `.env` 有更新時。再次執行 `從NAS拉取專案.bat` 會自動進入「更新模式」:不覆蓋您改過的檔案、不動 `.git`,`.env` 有差異時會先詢問並備份。

## 二、分支與合併流程

### 1. 分支和部署區的對應

```
feature/xxx(您自己的分支)
      │  在 GitLab 開 Merge Request
      ▼
develop ──── CI 自動部署 ───► 測試區(主機 2,https://giganexus-test.gigasolar.com.tw)
      │  專案負責人開 Merge Request
      ▼
main ─────── 負責人手動部署 ──► 正式區(主機 3)
```

| 分支 | 用途 | 誰可以推送 / 合併 |
| --- | --- | --- |
| `feature/*`、`fix/*`、`docs/*` | 個人開發用,隨時可推送,**不會觸發部署** | 任何人 |
| `develop` | 測試區;合併後 CI 會自動部署 | **只能透過 Merge Request 合併**,由專案負責人合併 |
| `main` | 正式區 | **只有專案負責人**可以合併 |

各專案目前的 CI 部署設定:

| 專案 | 推到 `develop` | 推到 `main` |
| --- | --- | --- |
| `giga-api-gateway-bff` | 自動部署測試區 | 在 GitLab Pipeline **手動按下**才部署正式區 |
| `GigaItApp`、`giga-Portal`、`giga-file-service`、`RustIt` | 自動部署測試區 | 尚未設定正式區部署 |
| `giga-observe`、`GigaNexusAI`(工作區文件)、`hello-world` | 沒有 CI | 沒有 CI |

> ⚠️ **測試區只有一套,所有人共用。** 合併進 `develop` 就等於部署到測試區,會影響其他人正在測的功能。合併前先在群組說一聲。

### 2. 日常開發步驟

**① 開始新工作:先拉取最新程式碼,再從最新的 `develop` 開分支**

開發新功能前**一定要先同步**,從過期的程式碼開分支,之後幾乎一定會衝突。先用 `git status` 確認沒有未提交的修改,再執行:

```bash
git status
git fetch origin
git switch develop
git pull origin develop
git switch -c feature/portal-survey
```

> `git fetch origin` 先取得 GitLab 上最新的分支清單;本機還沒有 `develop` 時,`git switch develop` 會自動建立並追蹤 `origin/develop`。

分支命名:`<類型>/<簡短英文描述>`,全小寫、用 `-` 連接。

| 類型 | 用途 | 範例 |
| --- | --- | --- |
| `feature/` | 新功能 | `feature/portal-survey` |
| `fix/` | 修 bug | `fix/login-redirect` |
| `docs/` | 只改文件 | `docs/api-readme` |
| `refactor/` | 重構(不改變行為) | `refactor/rbac-service` |

**② 開發與提交**

```bash
git status
git add <檔案>
git commit -m "feat(portal-api): 新增問卷調查 API"
```

提交訊息沿用專案慣例:`<類型>(<範圍>): <中文說明>`,類型用 `feat`、`fix`、`docs`、`refactor`、`chore`、`test`。

- 一次提交只做一件事;不要把無關的修改混在一起。
- **不要提交 `.env`、密碼、Token、金鑰**。`git add .` 前先看 `git status`,確認沒有機密檔案。

**③ 推送自己的分支**

```bash
git push -u origin feature/portal-survey
```

第一次推送加 `-u`,之後直接 `git push` 即可。

**④ 在 GitLab 開 Merge Request(MR)**

1. 推送後終端機會顯示建立 MR 的網址,點開即可;或到 GitLab 專案頁 → **Merge requests** → **New merge request**。
2. **Source branch** 選您的分支,**Target branch** 選 **`develop`**(不要選 `main`)。
3. 描述會自動帶入 MR 範本(`.gitlab/merge_request_templates/Default.md`),逐項填寫:
   - 做了什麼、為什麼
   - 怎麼測試的(本機測試結果、截圖)
   - 影響範圍:有沒有動到資料庫、權限代碼、路由、`.env`、CI/CD、其他 repo
   - 有處理衝突時,填「衝突處理」欄
4. 勾選 **Delete source branch when merge request is accepted**。
5. 指派專案負責人為 Reviewer。

**⑤ Review 與合併**

- 負責人 review 後合併,CI 自動部署到測試區,您再到測試區驗證。
- 需要修改時,在同一個分支繼續提交、推送,MR 會自動更新。

**⑥ 合併後清理**

```bash
git switch develop
git pull origin develop
git branch -d feature/portal-survey
```

### 3. 分支落後 `develop` 或有衝突時

別人的 MR 先合併後,您的分支可能落後或產生衝突。把最新的 `develop` 合併進您的分支:

```bash
git fetch origin
git merge origin/develop
```

**有衝突時先停下,不要急著解**:

1. 先整理衝突會**影響哪些功能或邏輯**:哪些檔案衝突、雙方各改了什麼、會影響哪些 API、畫面、權限代碼、資料庫或設定。用 AI 開發時,AI 會停下來列出這份報告,不會自己解衝突。
2. **把報告告知專案負責人並討論**,確認要保留哪些修改後再解。
3. 解衝突:逐一打開衝突檔案、保留討論後確認的內容、刪掉 `<<<<<<<`、`=======`、`>>>>>>>` 標記。lock 檔、資料庫 migration 等特定檔案的處理方式見工作區 `AGENT.md` §9.4。
4. 執行測試,再提交、推送:

```bash
git add <解決衝突的檔案>
git commit
git push
```

5. 在 MR 的「衝突處理」欄記錄:衝突檔案、決議內容、參與討論的人。

**不要**整份採用其中一方(例如 `git checkout --theirs`、`-X ours`)覆蓋別人的修改,也不要 `git push --force`。

### 4. 讓分支保持小而短

- 一個 MR 只做一個功能,盡量 **1~2 天內**合併。
- 分支放越久,和別人的衝突越大;大家都用 AI 開發,改動量往往比預期大,更要小步合併。
- 功能太大時拆成幾個 MR 依序合併。

## 三、用 AI 開發時的注意事項

1. **AI 會讀 `AGENT.md`**:各專案的程式規範、部署規則、分支規則都寫在裡面。請 AI 開工前先讀該專案的 `AGENT.md`。
2. **開工前先確認在自己的分支上**,不要讓 AI 在 `develop` 或 `main` 上直接改。
3. **不要讓 AI 推送 `develop` / `main`、不要 force push**(`git push --force`)。推送自己的分支可以。
4. **提交前自己看過 AI 的修改**(`git diff`)。AI 不知道其他同仁正在改什麼,也可能改到任務以外的檔案。
5. **機密不交給 AI**:不要把密碼、Token 貼進對話;需要密碼的指令請自己執行。
6. **寫入測試區資料庫或共用資料前先確認**:測試區是共用的,AI 的寫入會影響所有人。
7. **跨專案修改先找負責人**:要改的不是自己負責的 repo(例如 Gateway),先整理需求交給該 repo 的負責人。
8. **AI 遇到衝突會停下**:AI 合併遇到衝突時會先停下,列出影響的功能與邏輯。請把這份報告交給專案負責人討論,不要直接叫 AI「幫我解掉」。完整規範見工作區 `AGENT.md` §9。

---

## 四、禁止事項

| 不要做 | 原因 |
| --- | --- |
| 直接推送 `develop` 或 `main` | 會繞過 review 直接部署;分支已設保護,推送會被拒絕 |
| `git push --force` 到共用分支 | 會覆蓋別人的提交 |
| 提交 `.env`、密碼、Token、金鑰 | 進了 Git 歷史就很難清除 |
| 共用別人的 SSH 金鑰或 Token | 查不出是誰做的修改 |
| 用 NAS 拉取來更新程式碼 | 程式碼以 GitLab 為準,NAS 只是負責人每日備份 |

## 五、常見問題

**Q:`git pull` 後 `git status` 出現一堆修改,但內容好像沒變**
各 repo 已加入 `.gitattributes`,統一用 LF 換行,第一次更新後可能出現只有換行不同的檔案。先確認沒有實際差異:

```bash
git diff --ignore-cr-at-eol --stat
```

沒有列出檔案(或只列出您自己改過的)時,對那些只有換行不同的檔案執行 `git checkout -- <檔案>` 重新檢出即可。**自己改過、還沒提交的檔案不要執行**,會把修改丟掉。

**Q:推送時出現 `Permission denied (publickey)`**
SSH 金鑰沒有加到 GitLab,或加到別的帳號。重做「一、2」,並用 `ssh -T -p 2222 git@10.10.130.123` 確認顯示的是您的帳號。

**Q:推送時出現 `You are not allowed to push code to protected branches`**
您正在推送 `develop` 或 `main`。改成推送自己的分支,再開 MR:

```bash
git switch -c feature/<描述>
git push -u origin feature/<描述>
```

**Q:不小心在 `develop` 上提交了,還沒推送**
把提交搬到新分支,再讓本機 `develop` 回到遠端的狀態:

```bash
git switch -c feature/<描述>
git branch -f develop origin/develop
```

**Q:`npm install` 出現 401 / 404,裝不到 `@giganexus/*`**
`GITLAB_NPM_TOKEN` 沒設定或沒生效。確認「一、4」做完,並**重新開啟終端機**:

```powershell
echo $env:GITLAB_NPM_TOKEN
```

**Q:CI 失敗了怎麼辦**
GitLab 專案頁 → **Build** → **Pipelines**,點進失敗的 job 看 log。看不懂時把 log 貼給專案負責人(注意遮蔽 log 裡的機密)。
